# RCA — hi.tours / www.hi.tours custom-domain SSL handshake failure

## Problem statement
After a successful ("Clean") deploy, the app is live on the default URL
`https://tourlane-rebuild.emergent.host`, but the custom domains fail:
- `curl https://hi.tours/` and `curl https://www.hi.tours/` → `sslv3 alert handshake failure` (SSL alert 40)
- `openssl s_client -connect hi.tours:443 -servername hi.tours` → `no peer certificate available`
- `hi.tours` resolves to `172.66.2.113` (Cloudflare anycast)
- Control request to `https://www.cloudflare.com` from the same container returns 200 → container networking is fine. The edge simply has **no certificate** for these hostnames.

## What I verified (tool evidence)
- `describe_deployment_state`: `frontend_type=cloudflare`, active run `882f9e25…` status `success`, live on `https://tourlane-rebuild.emergent.host`. Both `www.hi.tours` and `hi.tours` show `verified: true`.
- `check_domain_status`: both domains `linked: true` → DNS A-record resolution points at our edge. DNS binding is NOT the problem.
- `list_domains` (the decisive evidence):
  - `hi.tours`  → `verified: true`, **`ssl_status: "initializing"`**, `ssl_validation_method: "http"`, provider `cloudflare`, `cf_custom_hostname_id: e8999903-556f-4b5a-bcd8-01665cf5b2af`, `root_redirect_enabled: true`
  - `www.hi.tours` → `verified: true`, **`ssl_status: "initializing"`**, `ssl_validation_method: "http"`, provider `cloudflare`, `cf_custom_hostname_id: e251b8d6-0465-4038-9a29-d2513008a18e`, `root_redirect_enabled: true`

## Root cause
The Cloudflare-for-SaaS **custom-hostname certificate is still in `initializing` for both `hi.tours` and `www.hi.tours` — it has never been issued.** With no issued cert, the Cloudflare edge has nothing to present during the TLS handshake, which is exactly what the probes show: SSL alert 40 / "no peer certificate available". The domains are linked and verified; only certificate issuance is incomplete.

Issuance is configured for **HTTP (HTTP-01 style) validation** (`ssl_validation_method: "http"`). HTTP validation requires Cloudflare to fetch a validation token over **plain HTTP at the hostname's origin path** (`http://hi.tours/.well-known/...`). This is being blocked because the apex `hi.tours` resolves to `172.66.2.113`, a Cloudflare **proxied** anycast address — i.e. the record is sitting behind the user's **own Cloudflare zone with the proxy turned on (orange cloud)**. The user's Cloudflare intercepts the HTTP validation request before it reaches our Cloudflare-for-SaaS fallback origin, so the challenge never completes and the cert stays pinned at `initializing`.

This matches the "initializing + http validation + resolves to a Cloudflare proxied IP" signature exactly. (A blocking CAA record is a secondary possibility but is less consistent with the evidence — a CAA block typically surfaces as `ssl_status: pending_validation`/`failed` rather than staying at `initializing`; the proxied-origin interception is the stronger explanation here.)

## Expected vs current DNS
- **Expected:** `hi.tours` and `www.hi.tours` should be **CNAME (or A) records pointing at the Emergent target, set to DNS-only (grey cloud)** so Cloudflare-for-SaaS can reach the origin and complete HTTP validation. On an apex, use the registrar's CNAME-flattening/ALIAS or the A record Emergent provides — but it must **not** be proxied by the user's own Cloudflare.
- **Current:** `hi.tours` → `172.66.2.113`, a **proxied** Cloudflare IP (orange cloud) in the user's own zone, which swallows the validation request.

## Exact steps the user must take
1. In **their own Cloudflare dashboard** (the zone that owns `hi.tours`), open **DNS** and find the records for `hi.tours` and `www.hi.tours`.
2. **Turn the proxy OFF (orange cloud → grey cloud / "DNS only")** on both records, so they point directly at the Emergent target and validation traffic reaches us. Confirm the record targets match what Emergent shows in **Deployment Panel → Domains**; re-copy them verbatim if they differ.
3. Check for a **CAA record** on the zone. If one exists, it must allow Cloudflare's CA — add `0 issue "pki.goog"` and `0 issue "letsencrypt.org"` (or remove the restrictive CAA). If no CAA exists, nothing to do.
4. Wait for DNS to propagate and for Cloudflare-for-SaaS to re-attempt validation. `ssl_status` should move `initializing → pending_validation → active`. Issuance typically completes within minutes to ~an hour after the proxy is disabled.
5. Re-test: `openssl s_client -connect hi.tours:443 -servername hi.tours` should return a real certificate, then `curl https://hi.tours/` and `curl https://www.hi.tours/` should succeed.

Meanwhile the app remains fully live and serving on `https://tourlane-rebuild.emergent.host` — nothing in the app or the deploy is broken.
